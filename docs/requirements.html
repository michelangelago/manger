Manger / Requirements

Functional requirements and use cases

The implemented scope, actors, acceptance criteria, and technical characteristics.

This is an as-built specification: it describes behavior present in the inspected source, not proposed features. Requirement IDs identify documentation entries, not runtime entities. Source files and automated evidence are listed for each capability.

Scope and actors

ActorImplemented responsibility
Telegram participantCan register, request help, and manage or browse the shared catalog. Catalog handlers do not require prior registration.
Registered userA Telegram sender mapped to a users row; accesses their own daily logs, consumed foods, goals, and summaries. This is a data condition, not a role or permission table.
OperatorConfigures the environment, runs migrations, starts the polling process, and runs tests. No operator/admin Telegram role is implemented.
External systemTelegram delivers updates and accepts bot responses through Nutgram. SQLite is local persistence, not a remote service.

Core use cases

Use caseSuccessful flowAlternative / failure flow
UC-01 · RegisterSend /start → resolve sender → save/upsert user → read stored row → return profile.Missing sender: return without mutation or reply. Existing sender: retain row and return welcome-back text.
UC-02 · Log a portionSend /eat or /dfoods -C → validate input → resolve registered user → find food → begin transaction → create/reuse dated daily row → insert entry → commit → reply.Invalid input, unregistered sender, or missing food: no insert. Database exception inside transaction: roll back both writes. A Telegram reply failure after commit does not undo the committed data.
UC-03 · View a periodParse optional date/period → resolve user → compute local calendar boundaries → query grouped food totals → optionally load today's goal → format summary.Invalid parameters show usage. Missing registration asks for /start. No consumption returns 0 kcal without creating data.
UC-04 · Manage goalParse flag → validate positive target when needed → resolve user → execute user-scoped operation → reply.Duplicate create does not overwrite. Update/delete/read do not create an absent goal.

Implemented technical characteristics

IDObserved implementationEvidence / boundary
TC-01PHP ^8.2 with Nutgram ^4 and phpdotenv ^5.6; CLI requires PDO SQLite.composer.json; app/database/connection.php. SQLite extension requirements are documented but are not declared as root Composer extension requirements.
TC-02Prepared SQL values and writable-column allowlists for generic CRUD.app/database/repositories/Repository.php. Generic methods are not ownership-aware; personal commands must use scoped methods.
TC-03Foreign keys enabled, exception-mode PDO, associative fetches, 5000 ms busy timeout.app/database/connection.php. This does not establish an availability or concurrency SLA.
TC-04Custom tests use a new in-memory database and FakeNutgram client per case.tests/Support/TestContext.php; tests/run.php. No live Telegram integration test is implied.
TC-05GitHub workflow configures PHP 8.2 and 8.5 checks on push, PR, and manual invocation..github/workflows/tests.yml. A workflow definition is not evidence that a hosted run has passed.
TC-06Static HTML guides, local CSS, and SVG diagrams work without a JavaScript CDN.docs/assets/style.css. No production web application is implemented by these docs.

No performance target, uptime target, recovery objective, or accessibility certification is established by the code. See Current limitations for absent capabilities.
