Manger / Database

Data model and persistence

SQLite tables, migrations, constraints, and repository operations.

SQLite is stored at storage/database.sqlite and created automatically by the connection. Foreign keys are enabled, errors throw PDO exceptions, and query results use associative arrays.

Migrations and tables

Run composer migrate after adding or updating the application. Completed migrations are recorded and skipped on subsequent runs. Each migration runs in a transaction. Add schema changes as new numbered files under app/database/migrations/.

TableMain fields and purpose
usersTelegram ID, name, and registration timestamp.
food_groupsGroup name.
foodsName, energy in kcal/100 g, and food group ID.
dailyName, user ID, and date; dated logs are unique per user and date.
daily_foodsDaily log ID, food ID, quantity in grams, and consumption timestamp.
calorie_goalsUser ID and positive daily calorie target; one goal per user.

daily_foods.diet_id references daily.id. New consumption timestamps include the timezone offset. Existing undated daily logs are preserved as legacy rows. Default group seeding preserves existing groups with matching names.

Daily log creation and its first consumption entry run in one transaction. A unique index on (user_id, date) prevents duplicate dated logs, and a failed entry does not leave a new empty log. Foreign keys prevent deleting referenced records.

Repository API

Repositories share these methods through Repository:

MethodResult
index(): arrayAll rows, ordered by ID.
create(array $data): intInserts a row and returns its ID.
read(int $id): ?arrayMatching row, or null.
update(int $id, array $data): boolUpdates writable fields; returns false if missing.
delete(int $id): boolDeletes a row; returns false if missing.

Empty data and unknown or read-only columns are rejected. Constraint violations throw PDO exceptions. UserRepository also provides save() and findByTelegramId(); foods and groups provide findByName(). Daily entries, logs, and goals provide queries scoped to the current user. Use those scoped methods when handling personal data in bot commands.

Specialized repository methods

RepositoryMethods and behavior
UserRepositorysave(telegramId, name) inserts or updates by Telegram ID; findByTelegramId() returns a row or null.
FoodGroupRepositoryfindByName() returns the first matching group, ignoring letter case.
FoodRepositoryfindByName() ignores letter case; indexByGroup(groupId) returns a grouped catalog, including empty groups. A null group ID selects all groups.
DailyRepositoryindexForUser(), findByDate(userId, date), and getOrCreateForDate(userId, date) scope logs by user and date.
DailyFoodRepositoryindexForUser(userId, dailyId) and readForUser(id, userId) return entries joined to food names and energy. The daily ID filter is optional.
DailyFoodRepositoryregisterConsumption(userId, foodId, quantity, now) creates or reuses the daily log and inserts consumption atomically.
DailyFoodRepositoryupdateForUser(id, userId, foodId, quantity) and deleteForUser(id, userId) enforce ownership in SQL.
DailyFoodRepositorysummarizeForUser(userId, startDate, endDate) groups consumption by food; start is inclusive and end is exclusive.
GoalRepositoryfindByUserId(), createForUser(), updateForUser(), and deleteForUser() access a user's single calorie goal.

Name uniqueness for catalog foods and groups is checked by the bot handlers. Unlike daily-date and goal uniqueness, it is not currently a database unique constraint. Generic repository methods are unscoped; bot handlers must use ownership-aware queries for personal data.
