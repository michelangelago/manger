Manger / Current limitations

Implementation boundaries

Observed limitations and absent capabilities, separated from implemented behavior.

These are implementation boundaries, not implemented requirements or a promised roadmap. They are included so the specification does not claim protections or features that the software lacks.

Observed limitations

IDCurrent behaviorConsequenceSource evidence
LIM-01Catalog commands do not enforce registration, ownership, or administrator permission.Any sender reaching these handlers can change the shared catalog.app/bot/commands/FoodCommand.php; app/bot/commands/FoodGroupCommand.php
LIM-02Consumption stores a food reference and grams, not the calorie/name snapshot.Changing catalog energy changes historical totals; name changes change displayed food names.app/database/repositories/DailyFoodRepository.php: summarizeForUser
LIM-03Some listings are built as one unbounded message: /food -I, /fgroup -I, /daily -I, /daily -R, /dfoods -I.Large results can exceed Telegram message limits. /gview splits output and /dview caps displayed foods; that handling is not shared by all commands.app/bot/commands/DailyFoodCommand.php; app/bot/commands/FoodCommand.php
LIM-04Food/group name uniqueness is checked before writing in application code only.Direct SQL/repository writes or competing writers can introduce duplicates; name lookup returns the first by ID.app/database/repositories/FoodRepository.php: findByName
LIM-05No update ID or idempotency key is persisted with consumed-food entries.Repeated /eat or create calls insert distinct entries; application-level exactly-once processing is not guaranteed.app/database/repositories/DailyFoodRepository.php: registerConsumption
LIM-06date is nullable, and migration 004 does not backfill legacy rows.Legacy logs remain in index output, but date read and period summaries do not resolve NULL-date logs.app/database/migrations/004_add_daily_date.php
LIM-07Personal data is filtered by sender, but replies use the invoking chat.There is no private-chat-only restriction; a user invoking a personal view in a group may expose their reply to that chat.app/bot/commands/DailyCommand.php
LIM-08Menu synchronization precedes polling and is not wrapped in application retry logic.An uncaught startup Telegram failure prevents reaching the polling call.app/bot/bot.php
LIM-09SQLite default NOCASE is used without a custom collation.Full Unicode-insensitive name lookup and normalization are not implemented.app/database/repositories/FoodGroupRepository.php: findByName
LIM-10/start registration is Telegram identity mapping, not an account/password system.There is no independent login, permission model, or user-deletion command.app/bot/commands/StartCommand.php
LIM-11PDO SQLite is needed at runtime but not declared in root composer.json require.Composer platform checks alone do not verify this application-specific extension requirement.composer.json; app/database/connection.php

Capabilities not implemented

  • Meal categories, meal templates, favorites, consumption backdating, reminders, charts, macros, CSV export, and goal history.
  • Administrative catalog roles, per-user timezone settings, account data export/deletion commands, or per-user food catalogs.
  • Database backups/restores, service supervision, deployment automation, health monitoring, and an application-specific operational alerting system.
  • An interactive web app or HTTP API: public/index.php is a plain environment status response; docs/ contains static documentation.
  • Nutrition calculations beyond calories: no protein, carbohydrate, fat, fiber, or serving-unit conversion fields exist.

Release interpretation

Automated tests and a CI workflow exist. They do not establish production readiness, an availability SLA, a completed hosted CI run, security certification, or support for high-volume deployment. This documentation records what the code implements; it does not change these boundaries.
