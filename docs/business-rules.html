Manger / Business rules

Business rules and enforcement

Rules verified in handlers, repositories, schema constraints, and view helpers.

The enforcement column matters: a command validation is not automatically a database constraint. These rules describe current implementation, including restrictions and exceptions. They are linked from the functional requirements.

Business rule catalog

BR-01 · Identity and profile

Telegram sender ID is the external identity. users.telegram_id is unique. /start inserts or updates the name while preserving the original row and registration time.

Enforcement: Database UNIQUE plus handler behavior

Evidence: app/database/repositories/UserRepository.php: UserRepository::save; StartCommand

BR-02 · Personal ownership

Personal commands find the application user from the Telegram sender. Daily and goal queries are scoped to that user. Missing registration asks for /start; a foreign entry ID is reported as not found.

Enforcement: Handlers and scoped SQL; generic repository methods remain unscoped

Evidence: app/bot/commands/DailyFoodCommand.php: DailyFoodCommand; DailyCommand; DailyViewCommand; GoalCommand

BR-03 · Flags and discovery

Operation flags are -I/-C/-R/-U/-D and are case-insensitive. /daily supports only -I/-R; /goal excludes -I. /dview uses separate -D/-W/-M/-Y period flags. Root commands are registered in commands.php.

Enforcement: Input parsing; no legacy word-operation aliases

Evidence: app/bot/support/CommandInput.php: CommandInput::operation; command routing

BR-04 · Shared catalog

Food groups and foods are global. Catalog create/read/update/delete and /gview have no registration or admin permission check. There is no owner field on either catalog table.

Enforcement: Current behavior; not an authorization policy for public deployment

Evidence: app/bot/commands/FoodCommand.php: FoodGroupCommand; FoodCommand; GroupViewCommand

BR-05 · Catalog duplicate names

Handlers reject a create or rename when findByName finds another row. Updating the same row to its current name is allowed. There is no database UNIQUE constraint on food/group names.

Enforcement: Application-level check only; concurrent/direct inserts are not constrained by name

Evidence: app/bot/commands/FoodGroupCommand.php: FoodCommand; FoodGroupCommand

BR-06 · Name lookup

Food and group lookups use SQLite COLLATE NOCASE. Names may be single words or double-quoted phrases; outer whitespace is trimmed. Embedded double-quote escaping is not supported. SQLite default NOCASE is not full Unicode case folding.

Enforcement: SQL collation and parser; no Unicode normalization layer

Evidence: app/database/repositories/FoodRepository.php: findByName; CommandInput::tokens

BR-07 · Catalog energy

Food create/update accepts a non-negative whole integer for energy in kcal per 100 g. Zero is valid. Update supplies new name, energy, and group. The foods table has INTEGER affinity and NOT NULL but no positivity/type CHECK.

Enforcement: Handler validation; not a universal database invariant

Evidence: app/bot/commands/FoodCommand.php: FoodCommand::__invoke

BR-08 · Portion quantity and entry IDs

Consumption create/update requires positive whole grams. Read/update/delete entry IDs must be positive integers within the PHP integer range. Repeated logging of a food creates separate entries.

Enforcement: Handler validation; daily_foods.quantity has no positive CHECK

Evidence: app/bot/commands/DailyFoodCommand.php: DailyFoodCommand; CommandInput::positiveInteger

BR-09 · Relationships by name at the interface

Food create/update resolves a group name before persisting food_group_id. Consumption create/update resolves a food name before persisting food_id. Missing references reject the command before writing.

Enforcement: Handlers and repository lookups; IDs remain the relational keys

Evidence: app/bot/commands/FoodCommand.php: FoodCommand; DailyFoodCommand

BR-10 · One dated log per user and date

New logs use the local YYYY-MM-DD date for both name and date. UNIQUE(user_id,date) enforces one dated row per user/day. date remains nullable for pre-migration legacy rows, so the index does not constrain multiple NULL dates.

Enforcement: Database unique index for non-null dates; no universal NOT NULL date constraint

Evidence: app/database/migrations/004_add_daily_date.php: DailyRepository::getOrCreateForDate

BR-11 · Clock and day selection

APP_TIMEZONE defaults to America/Recife. New consumption uses now in that timezone with an offset timestamp. Creation has no backdate argument. /daily -R and /dview default to the current local date.

Enforcement: Configured DateTimeZone and injected clock

Evidence: app/bot/bootstrap.php: bootstrap; dated handlers

BR-12 · Atomic first consumption

registerConsumption begins a transaction, inserts/reuses the dated log, inserts the consumed food, then commits. An exception rolls the transaction back. No daily log is created merely because a calendar day exists.

Enforcement: Transaction for both inserts; no scheduled daily-row job

Evidence: app/database/repositories/DailyFoodRepository.php: DailyFoodRepository::registerConsumption

BR-13 · Consumption update semantics

Only food_id and quantity are changed by the user-scoped update. The daily reference and consumed_at remain unchanged, including when the update is made on another day.

Enforcement: Scoped UPDATE statement

Evidence: app/database/repositories/DailyFoodRepository.php: DailyFoodRepository::updateForUser

BR-14 · Consumption deletion semantics

Deleting a consumed-food entry does not delete its daily row. Logging another portion on the same day reuses that row.

Enforcement: Scoped DELETE of daily_foods only

Evidence: app/database/repositories/DailyFoodRepository.php: DailyFoodRepository::deleteForUser

BR-15 · Referenced-row deletion

Foreign keys use SQLite default NO ACTION; no cascades are declared. Handlers explain blocked group deletion when foods reference it and blocked food deletion when consumed entries reference it.

Enforcement: Foreign-key enforcement enabled by connection.php

Evidence: app/database/migrations/002_create_food_tables.php: FoodCommand and FoodGroupCommand delete paths

BR-16 · Calorie calculation and history

Calories = current foods.energy × quantity / 100. Daily detail totals are formatted to two decimals; compact summaries round to two decimals and strip trailing zeros. Energy is not snapshotted on consumption; catalog edits can change historical totals.

Enforcement: Calculated at read time; no immutable nutritional history

Evidence: app/bot/support/DailyFoodView.php: DailyFoodView; DailyFoodRepository::summarizeForUser

BR-17 · Period boundaries

-D selects a local day; -W selects Monday–Sunday; -M and -Y select calendar month/year. The date identifies the containing period. SQL compares daily.date with an inclusive start and exclusive next-period date.

Enforcement: Calendar arithmetic and dated-log SQL; legacy NULL-date rows are excluded

Evidence: app/bot/commands/DailyViewCommand.php: DailyViewCommand; summarizeForUser

BR-18 · Compact summary visibility

Repeated entries are grouped by food ID and name. Rows are ordered by total calories descending, then name and ID. Up to 15 foods are shown, names over 80 characters are shortened, and totals include undisplayed foods.

Enforcement: Presentation limit; not a query limit on total calories

Evidence: app/bot/support/DailySummaryView.php: DailySummaryView::render

BR-19 · Group visualization

/gview groups and sorts the catalog by group/name, includes empty groups, and filters by group name if supplied. It shortens names to 80 characters and starts a new message before exceeding 3500 bytes.

Enforcement: Only this listing uses that message-splitting helper

Evidence: app/bot/support/GroupFoodView.php: FoodRepository::indexByGroup; GroupFoodView::pages

BR-20 · Goal cardinality and value

A user may have zero or one calorie goal. calories must be an SQLite integer greater than zero; the handler requires positive whole kcal/day. Goals are user-owned current settings.

Enforcement: Database UNIQUE(user_id), FK, and CHECK

Evidence: app/database/migrations/005_create_calorie_goals.php: GoalRepository; goal migration

BR-21 · Goal operation semantics

Create uses ON CONFLICT(user_id) DO NOTHING and does not overwrite. Update and delete only affect an existing row for the current user. None of read/update/delete creates a missing row.

Enforcement: SQL operation semantics

Evidence: app/database/repositories/GoalRepository.php: GoalRepository scoped operations

BR-22 · Goal comparison

A goal comparison appears only for a day view matching today in the configured timezone. Remaining = goal - consumed; a negative difference is shown as Over goal with its absolute magnitude. Goal history is not stored.

Enforcement: Presentation condition; no weekly/yearly goal or historical target

Evidence: app/bot/support/DailySummaryView.php: DailyViewCommand; DailySummaryView

BR-23 · Dates and invalid input

Dates must round-trip as YYYY-MM-DD through DateTimeImmutable; invalid calendar dates are rejected. Flags, argument counts, missing names, and non-integer portions return command usage. Valid personal commands still require registration.

Enforcement: Command validation; not a CHECK on daily.date

Evidence: app/bot/support/CommandInput.php: CommandInput::validDate and handlers

BR-24 · Migration and seed behavior

The runner sorts numbered PHP files, records completed filenames, and wraps each pending migration in a transaction. The seed inserts fruits, vegetables, grains, protein, dairy, fats only if no NOCASE name match exists. Re-running a completed migration does not restore deleted defaults.

Enforcement: Runner bookkeeping plus seed existence query

Evidence: app/database/migrate.php: migrate.php and seed

BR-25 · Read-only views

Daily index/read, /dview, and /gview do not create daily logs. Daily has no create/update/delete Telegram operations. Generic repository CRUD remains available to internal PHP callers.

Enforcement: Bot command surface, distinct from repository capabilities

Evidence: app/bot/commands/DailyCommand.php: DailyCommand; view handlers

Worked example: consumption and a goal

With Apple at 52 kcal/100 g, two portions of 150 g and 100 g total 130 kcal. A daily goal of 2000 kcal leaves 1870 kcal. Updating the catalog energy to 60 makes those existing portions total 150 kcal, because no per-entry energy snapshot exists.

Important boundaries

  • An owned query protects database selection, not the visibility of the Telegram chat itself. The bot replies in the invoking chat; there is no private-chat-only gate.
  • Name duplicate checks and numeric validation apply through these handlers. Direct generic repository writes can bypass validations not backed by database constraints.
  • The unique dated-log key does not prevent an intentional second food entry. Telegram update IDs are not persisted for consumption deduplication.
  • Foreign keys block deletion but do not prevent a catalog energy or name change affecting an existing entry's current read-time display.
